Platform Architecture

How Every Agent is Built

Three files per agent, three layers of the architecture.

agent.yml

The wiring layer. Defines the model, reasoning effort, tool connections, variable pre-loads, and structured output schema. This is what Treasure AI reads at deployment time.

prompt.md

The behavior layer. Defines goals, guardrails, escalation rules, and what the agent must never do. The LLM reads this on every conversation turn to decide how to respond.

Knowledge Bases

The data layer. Table-based KBs run td_query against live Treasure Data databases. Text-based KBs store policies, playbooks, and FAQs the agent can read and cite.

The Agentic Loop
User message
->
Agent reads prompt.md
->
Calls tool or KB
->
KB queries TD data
->
Agent responds
->
Writes output to CDP

The output schema at the end of every agent closes the loop - structured data from each conversation flows back into Treasure Data to update customer profiles, refine segments, and trigger downstream journeys. This is what makes the system agentic rather than just conversational.

TV
Media Streaming

Subscriber Re-engagement Agent

Re-engages at-risk subscribers using personalized content recommendations before they cancel.

3 Knowledge Bases Variables reasoning: medium test.yml included
Logic and Context

Media subscribers churn fastest when content consumption drops. The re-engagement window is narrow - once a subscriber mentally cancels, win-back rates drop sharply. The agent is triggered for subscribers whose subscription expires within 14 days and who have had no content plays in 30 or more days.

The core logic is personalization-first: the agent pre-loads the subscriber's profile via a variables block before the conversation starts, so it already knows their tier, expiry date, and viewing history on the first message. Content recommendations are pulled from a live content catalog KB, matched against genre preferences.

Urgency is used once and only once. If expiry is within 7 days, the agent acknowledges it clearly - then never repeats it. Repeated urgency signals trigger churn defensiveness.

Build Process
  1. Identified the at-risk subscriber segment using CDP behavioral data - no plays in 30+ days with expiry approaching
  2. Designed three KB types: subscriber profiles (table, LOOKUP), content catalog (table, SEARCH), subscriber FAQ (text, READ_TEXT)
  3. Added a variables block to pre-load subscriber context using subscriber_id before conversation opens - eliminates a tool iteration on the first message
  4. Wrote prompt guardrails: urgency used once, no fabricated offers, no cross-subscriber data leakage
  5. Defined output schema capturing intent (retained/at_risk/churned), action taken, and recommended titles for CDP feedback loop
  6. Wrote test.yml with smoke, behavior, security, and multi-round regression tests
Business Value

Churn costs a media streaming business 5x to 10x more than retention. A re-engagement agent running at scale replaces what would otherwise require a large outbound support team contacting subscribers manually.

  • Reduces subscriber churn by intercepting at-risk users before cancellation intent solidifies
  • Increases content plays from dormant subscribers through personalized title surfacing
  • Scales 1:1 personalization across millions of subscribers simultaneously
  • Output data feeds back into CDP segments, improving future journey targeting

BG
Retail Ecommerce

Abandoned Cart Recovery Agent

Diagnoses why a customer abandoned their cart and removes the specific barrier before offering any promotion.

3 Knowledge Bases Variables (2) reasoning: low Barrier detection logic
Logic and Context

Roughly 70% of ecommerce carts are abandoned. The most common mistake in recovery is leading with a discount - which trains customers to abandon carts intentionally to get offers. This agent is designed around barrier diagnosis first.

The agent uses two variables to pre-load context: the customer's profile (cart contents, loyalty tier, order history) and the active promotions list. This means it arrives at the conversation already knowing what the customer left behind and what offers are currently valid.

Promotions are only surfaced under two conditions: the customer explicitly raises price as the barrier, or the cart value exceeds $150 and the customer is not already a Platinum member. Otherwise, the agent addresses product uncertainty, shipping concerns, or distraction - the more common barriers.

Build Process
  1. Identified cart abandonment as the highest-volume recovery use case in retail, with the constraint that discount-first logic damages long-term margin
  2. Designed barrier taxonomy: price, shipping, product uncertainty, distraction - each requires a different response strategy
  3. Built customer profiles KB (table, LOOKUP) and product catalog KB (table, SEARCH) for personalization and product question handling
  4. Added promotions FAQ as a text KB and pre-loaded it via variables so the agent does not need to call a tool to check eligibility
  5. Wrote prompt logic with conditional promotion gate - price sensitivity must be confirmed before any offer is made
  6. Output schema captures outcome, barrier identified, whether a promotion was offered, and cart value for ROI tracking
Business Value

Cart abandonment represents recoverable revenue that the business already spent to acquire. An agent that diagnoses the actual barrier converts at a higher rate than a generic discount blast, at lower cost to margin.

  • Recovers revenue from customers who had genuine intent to purchase
  • Protects margin by reserving discounts for price-sensitive customers only
  • Product uncertainty responses use live inventory data - no hallucinated specs or availability claims
  • Loyalty-tier awareness surfaces member benefits for Gold/Platinum customers without offering discounts they don't need

LY
CPG Loyalty

Loyalty and Shopper Insights Agent

Makes loyalty tangible for shoppers by showing exactly what their points are worth and surfacing the most relevant rewards.

2 Table KBs 1 Text KB Web Search Tool Tier-aware messaging
Logic and Context

CPG loyalty programs fail not because the rewards are bad, but because shoppers do not understand what their points are worth or feel the program is too abstract. The agent's core logic is to make loyalty concrete: "you have 840 points - that is enough for this specific reward."

The agent uses three tool types. The shopper profiles KB provides live points balance, tier, and purchase history. The rewards catalog KB surfaces the best available redemption for that shopper's current balance. The brand FAQ handles product and sustainability questions accurately. The web search tool is the differentiator - it extends the agent beyond static KB content to find current retailer availability or brand news in real time.

Tier-aware messaging adjusts the entire conversation tone. Bronze shoppers hear about the path to Silver. Silver shoppers hear about exclusive events. Gold shoppers are treated as brand advocates and asked for feedback.

Build Process
  1. Identified that CPG loyalty agents fail most often by abstracting points - solved with a concrete points-to-reward translation rule in the prompt
  2. Built shopper profiles KB (table, LOOKUP) with tier, points balance, expiry date, and preferred retailers
  3. Built rewards catalog KB (table, SEARCH) filtered to available rewards only - agent cannot surface unavailable or expired rewards
  4. Added brand FAQ as a text KB for product, sustainability, and policy questions
  5. Wired in web_search tool as a fourth tool type - used only when the question requires live data not in static KBs
  6. Designed tier-aware prompt logic with distinct behavior for Bronze, Silver, and Gold tiers
  7. Output schema captures loyalty intent, whether points were discussed, whether an offer was surfaced, and brand sentiment
Business Value

CPG brands invest heavily in loyalty programs that underperform because engagement is low. An agent that makes loyalty feel real and personalized increases redemption rates and repeat purchase frequency.

  • Increases points redemption rate - the clearest sign of an engaged loyalty member
  • Drives repeat purchase by surfacing rewards tied to upcoming purchase occasions
  • Gold-tier shopper engagement generates brand advocacy and product feedback at scale
  • Brand sentiment output feeds into CDP for segment refinement and campaign targeting

LQ
Automotive

Lead Qualification Agent

Qualifies inbound automotive leads through natural conversation and outputs a five-field score that routes buyers to the right next step.

3 Knowledge Bases reasoning: high 5-field qualification output CRM integration ready
Logic and Context

Automotive dealerships lose high-value leads because qualification happens inconsistently - some buyers get routed to a sales advisor immediately, others go cold in a generic nurture flow. The agent creates a consistent, structured qualification process across every inbound interaction.

This agent uses reasoning_effort: high because qualification decisions have direct downstream consequences. A misclassified hot lead that goes into a cold nurture journey represents thousands of dollars in lost revenue. The higher reasoning effort means the agent considers more signals before scoring a lead.

The agent leads with understanding, not pitching. It asks about the buyer's use case before suggesting models, checks lead history to recognize returning customers, and only surfaces specific inventory after understanding the stated need. Financing rates are never quoted - that always routes to the finance team.

Build Process
  1. Identified lead routing as the highest-value use case - inconsistent qualification is the primary source of lost automotive revenue at scale
  2. Designed four qualification tiers (hot, warm, cold, unqualified) with explicit signal definitions in the prompt
  3. Set reasoning_effort: high to ensure qualification judgment considers all available signals before scoring
  4. Built lead profiles KB (table, LOOKUP) with prior vehicle, service history, and previous inquiries for returning customer recognition
  5. Built vehicle inventory KB (table, SEARCH) filtered to available vehicles only - prevents overselling unavailable stock
  6. Added sales FAQ as a text KB for financing, trade-in, and test drive questions - with explicit guardrail against quoting rates
  7. Output schema captures five fields: qualification score, purchase timeline, vehicle interest, financing interest, trade-in interest, and recommended action
Business Value

A hot lead that waits 24 hours for a human callback converts at a fraction of the rate of one contacted within 5 minutes. An agent that qualifies and routes in real time closes the gap between lead capture and sales engagement.

  • Increases sales conversion by routing hot leads to advisors in real time
  • Reduces wasted sales team time on cold or unqualified leads
  • Returning customer recognition builds trust and shortens the qualification conversation
  • Structured output integrates directly with CRM and journey orchestration workflows

B2B SaaS

Churn Risk Intervention Agent

Diagnoses at-risk B2B SaaS accounts, consults an intervention playbook, and escalates to the CSM when thresholds are met.

3 Knowledge Bases Success Playbook KB reasoning: high CSM escalation logic
Logic and Context

B2B SaaS churn is expensive and often preventable if caught early. The problem is that Customer Success Managers cannot monitor every account in real time - at-risk signals appear in the data weeks before a renewal conversation, but no one sees them in time.

The agent solves this by operating at scale across all accounts continuously. It uses reasoning_effort: high because root cause diagnosis requires genuine inference - the reason an account has low adoption is often not the obvious one. Internal change, missing features, poor onboarding, and pricing pressure all present with similar usage patterns but require completely different interventions.

The Success Playbooks KB is the architectural differentiator. Rather than encoding intervention logic in the prompt, it lives in a separate text KB the agent consults at runtime. This makes the playbooks updatable without redeploying the agent - a critical requirement for a living CS practice.

Build Process
  1. Identified root cause classification as the core challenge - same symptoms, different causes require different interventions
  2. Built account profiles KB (table, LOOKUP) with health score, seat utilization, feature adoption gaps, open tickets, NPS score, and renewal date
  3. Built product docs KB (table, SEARCH) for accurate feature and how-to responses - prevents hallucinated product guidance
  4. Designed Success Playbooks as a text KB rather than prompt logic - intervention sequences by risk tier that can be updated without redeployment
  5. Set reasoning_effort: high for accurate root cause diagnosis across six possible causes
  6. Wrote escalation rules with hard thresholds: competitor mention, pricing discussion, frustrated support, renewal within 60 days with high risk
  7. Output schema captures churn risk level, root cause, intervention taken, CSM escalation flag, and renewal at risk flag
Business Value

In B2B SaaS, annual recurring revenue is the primary business metric and churn directly erodes it. An agent that intercepts at-risk accounts before the renewal conversation preserves revenue that would otherwise require expensive win-back campaigns or be lost entirely.

  • Scales CS coverage without scaling headcount - agent monitors every account in real time
  • Root cause classification enables precise interventions rather than generic check-ins
  • Escalation flags ensure human CSMs focus on the accounts that genuinely need them
  • Output feeds CDP segments for renewal risk dashboards and proactive outreach journeys

Customer Success Orchestrator

Routes incoming customer requests to specialist agents using agent-to-agent tool wiring. The most advanced pattern in the portfolio.

Agent-to-agent tools reasoning: high output_mode: RETURN test.yml included
Logic and Context

This agent uses a fundamentally different architecture from the other five. Instead of knowledge bases as tools, it wires two specialist agents as tools - the Subscriber Re-engagement Agent and the Churn Risk Intervention Agent. This is the agent-to-agent pattern.

The orchestrator's job is to triage and delegate, not to resolve. When a message arrives, it reads the prompt's routing rules to determine whether the customer is a B2C media subscriber or a B2B SaaS account. It then calls the appropriate specialist with the full customer message as context and relays the response. The customer sees one seamless conversation.

output_mode: RETURN on both specialist tools means their responses come back to the orchestrator before delivery, allowing synthesis. If output_mode were SHOW, the specialist's response would stream directly to the customer - useful in some cases, but not here where the orchestrator needs to control the handoff.

Build Process
  1. Identified the use case: enterprises with multiple customer types hitting one entry point need intelligent routing, not a single monolithic agent
  2. Deployed specialist agents first (media-streaming and b2b-saas) - orchestrator requires them to exist before it can reference them via @ref
  3. Wired specialist agents as tools using type: agent rather than type: knowledge_base - the key architectural difference
  4. Set output_mode: RETURN on both tools so responses return to orchestrator for synthesis before delivery
  5. Wrote routing rules in prompt.md with keyword signals for B2C vs B2B disambiguation
  6. Added explicit guardrail: do not expose specialist agent names to the customer
  7. Wrote test cases covering routing accuracy, ambiguous input handling, and specialist name exposure

Business Value

Large enterprises often have multiple customer types - individual consumers and business accounts - contacting the same support entry point. Without routing, both get generic responses or reach the wrong specialist. The orchestrator eliminates that friction.

  • Unifies multiple agent capabilities behind one customer-facing interface
  • Reduces wrong-team escalations and misrouted support contacts
  • Scales to additional specialist agents without changing the customer experience
  • Routing decision output feeds CDP for customer type classification and journey assignment
