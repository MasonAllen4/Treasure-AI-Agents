Treasure AI
Agent Portfolio

Six agents built across five industries using Treasure AI Foundry. Each one was designed around a different architectural pattern - simple KB lookup, variables pre-loading, web search, and full agent-to-agent orchestration - to cover the range of what gets built in real client deployments.

I used Treasure AI's AI assistant to research which industries see the most CDP deployments. It surfaced Media/Entertainment, Retail, CPG, Automotive, and B2B SaaS. What those industries share is a specific, measurable data problem - subscriber churn, cart abandonment, loyalty drop-off, lead quality, account health - where activating first-party data actually moves a number.

Platform Architecture

How Every Agent is Built

Three files per agent, three layers of the architecture.

agent.yml

The wiring layer. Defines which model runs, the reasoning effort level, how tools connect, any variables to pre-load, and what the output looks like. This is what Treasure AI reads when the agent deploys.

prompt.md

The behavior layer. Goals, guardrails, escalation rules, hard limits. The LLM reads this on every turn.

Knowledge Bases

The data layer. Table KBs query live Treasure Data via td_query. Text KBs hold policies, playbooks, and FAQs the agent can pull from mid-conversation.

The Agentic Loop
User message
->
Agent reads prompt.md
->
Calls tool or KB
->
KB queries TD data
->
Agent responds
->
Writes output to CDP

The output schema closes the loop. Every conversation writes structured data back into Treasure Data - profiles update, segments refine, journeys trigger downstream. That's what separates this from a chatbot.

TV
Media Streaming

Subscriber Re-engagement Agent

Re-engages at-risk subscribers using personalized content recommendations before they cancel.

3 Knowledge Bases Variables reasoning: medium test.yml included
Logic and Context

Subscribers churn fastest when they stop watching. The re-engagement window is short - once someone has mentally decided to cancel, win-back rates drop hard. This agent targets subscribers within 14 days of expiry who haven't played anything in 30 or more days.

The design decision here was to pre-load the subscriber's profile using the variables block before the conversation opens. By the time the first message arrives, the agent already knows their tier, expiry date, and watch history - no first-turn tool call needed. Recommendations pull from a live content catalog KB matched to genre preferences.

Urgency gets used once. If expiry is within 7 days, the agent states it clearly and moves on. Repeating it creates defensiveness and kills the conversation.

Build Process
  1. Identified the at-risk subscriber segment using CDP behavioral data - no plays in 30+ days with expiry approaching
  2. Designed three KB types: subscriber profiles (table, LOOKUP), content catalog (table, SEARCH), subscriber FAQ (text, READ_TEXT)
  3. Added a variables block to pre-load subscriber context using subscriber_id before conversation opens - eliminates a tool iteration on the first message
  4. Wrote prompt guardrails: urgency used once, no fabricated offers, no cross-subscriber data leakage
  5. Defined output schema capturing intent (retained/at_risk/churned), action taken, and recommended titles for CDP feedback loop
  6. Wrote test.yml with smoke, behavior, security, and multi-round regression tests
Business Value

Keeping a subscriber costs a fraction of winning one back after they've cancelled. At scale, this agent covers ground that would otherwise need a large outbound team working through lists manually.

  • Catches at-risk subscribers before they've made up their mind to cancel
  • Gets dormant subscribers watching again by surfacing titles they're actually likely to play
  • Delivers personalized outreach across millions of subscribers at the same time
  • Every conversation writes back to the CDP, sharpening future segment targeting

BG
Retail Ecommerce

Abandoned Cart Recovery Agent

Diagnoses why a customer abandoned their cart and removes the specific barrier before offering any promotion.

3 Knowledge Bases Variables (2) reasoning: low Barrier detection logic
Logic and Context

About 70% of ecommerce carts get abandoned. The most common recovery mistake is leading with a discount - which trains customers to abandon on purpose to get an offer. This agent leads with barrier diagnosis, not discounts.

Two variables pre-load before the conversation starts: the customer's profile - cart contents, loyalty tier, order history - and the active promotions list. The agent arrives already knowing what was left in the cart and what offers are on the table.

Promotions only come up under two conditions: the customer brings up price, or the cart is over $150 and they're not already a Platinum member. Everything else - product questions, shipping concerns, getting distracted - gets handled directly without touching the offers.

Build Process
  1. Identified cart abandonment as the highest-volume recovery use case in retail, with the constraint that discount-first logic damages long-term margin
  2. Designed barrier taxonomy: price, shipping, product uncertainty, distraction - each requires a different response strategy
  3. Built customer profiles KB (table, LOOKUP) and product catalog KB (table, SEARCH) for personalization and product question handling
  4. Added promotions FAQ as a text KB and pre-loaded it via variables so the agent does not need to call a tool to check eligibility
  5. Wrote prompt logic with conditional promotion gate - price sensitivity must be confirmed before any offer is made
  6. Output schema captures outcome, barrier identified, whether a promotion was offered, and cart value for ROI tracking
Business Value

Cart abandonment is recoverable revenue. The customer showed intent - they just didn't finish. An agent that finds the real barrier converts better than a generic discount blast, and doesn't train people to abandon on purpose.

  • Recovers carts from customers who actually wanted to buy
  • Protects margin by not handing out discounts to customers who weren't asking for one
  • Product question responses pull from live inventory - no guessing on specs or availability
  • Gold and Platinum members get reminded of their benefits, not a discount they don't need

LY
CPG Loyalty

Loyalty and Shopper Insights Agent

Makes loyalty tangible for shoppers by showing exactly what their points are worth and surfacing the most relevant rewards.

2 Table KBs 1 Text KB Web Search Tool Tier-aware messaging
Logic and Context

CPG loyalty programs underperform not because the rewards are bad, but because shoppers have no idea what their points are worth. The program feels abstract. The agent's core rule is to make it concrete: "you have 840 points - that's enough for this specific reward."

There are four tools at play. Shopper profiles KB for live points balance, tier, and purchase history. Rewards catalog KB to surface the best available redemption for the current balance. Brand FAQ for product and sustainability questions. The web search tool is what separates this one from the others - it handles questions about retailer availability or brand news that static KBs can't answer.

The tone shifts based on tier. Bronze shoppers hear what it takes to reach Silver. Silver shoppers get told about events and exclusive access. Gold shoppers get treated like brand advocates and asked what they think.

Build Process
  1. Identified that CPG loyalty agents fail most often by abstracting points - solved with a concrete points-to-reward translation rule in the prompt
  2. Built shopper profiles KB (table, LOOKUP) with tier, points balance, expiry date, and preferred retailers
  3. Built rewards catalog KB (table, SEARCH) filtered to available rewards only - agent cannot surface unavailable or expired rewards
  4. Added brand FAQ as a text KB for product, sustainability, and policy questions
  5. Wired in web_search tool as a fourth tool type - used only when the question requires live data not in static KBs
  6. Designed tier-aware prompt logic with distinct behavior for Bronze, Silver, and Gold tiers
  7. Output schema captures loyalty intent, whether points were discussed, whether an offer was surfaced, and brand sentiment
Business Value

Most CPG loyalty programs underperform because members aren't actually engaged. When shoppers understand what their points are worth, redemption rates go up and they buy more often.

  • Increases points redemption - the clearest sign of an engaged loyalty member
  • Drives repeat purchase by surfacing rewards tied to upcoming purchase occasions
  • Gold-tier shoppers generate brand feedback and advocacy at scale
  • Brand sentiment output feeds CDP for segment refinement and campaign targeting

LQ
Automotive

Lead Qualification Agent

Qualifies inbound automotive leads through natural conversation and outputs a five-field score that routes buyers to the right next step.

3 Knowledge Bases reasoning: high 5-field qualification output CRM integration ready
Logic and Context

Dealerships lose leads because qualification is inconsistent. One buyer gets an advisor on the phone in minutes, another lands in a generic email nurture and goes cold. This agent makes that process consistent on every inbound interaction.

reasoning_effort is set to high here. A hot lead that gets scored cold and dropped into a nurture sequence represents real lost revenue. The higher setting means the agent considers more signals before calling it.

The agent asks before it sells. Use case first, then inventory. Lead history gets checked so returning customers are recognized. Financing rates are never quoted - that's a hard guardrail that routes straight to the finance team.

Build Process
  1. Identified lead routing as the highest-value use case - inconsistent qualification is the primary source of lost automotive revenue at scale
  2. Designed four qualification tiers (hot, warm, cold, unqualified) with explicit signal definitions in the prompt
  3. Set reasoning_effort: high to ensure qualification judgment considers all available signals before scoring
  4. Built lead profiles KB (table, LOOKUP) with prior vehicle, service history, and previous inquiries for returning customer recognition
  5. Built vehicle inventory KB (table, SEARCH) filtered to available vehicles only - prevents overselling unavailable stock
  6. Added sales FAQ as a text KB for financing, trade-in, and test drive questions - with explicit guardrail against quoting rates
  7. Output schema captures five fields: qualification score, purchase timeline, vehicle interest, financing interest, trade-in interest, and recommended action
Business Value

A hot lead contacted within 5 minutes converts at a much higher rate than one that waits 24 hours for a callback. An agent that qualifies and routes in real time closes the gap between lead capture and actual sales engagement.

  • Hot leads get to an advisor immediately instead of sitting in a queue
  • Sales team time goes to leads that are actually ready to buy
  • Returning customers get recognized, which shortens the conversation and builds trust
  • Structured output plugs directly into CRM and journey orchestration

CS
B2B SaaS

Churn Risk Intervention Agent

Diagnoses at-risk B2B SaaS accounts, consults an intervention playbook, and escalates to the CSM when thresholds are met.

3 Knowledge Bases Success Playbook KB reasoning: high CSM escalation logic
Logic and Context

B2B SaaS churn is expensive and most of it is preventable if you catch it early enough. The problem is that CSMs can't watch every account. At-risk signals show up in the data weeks before a renewal conversation - they just go unnoticed.

The agent runs across all accounts continuously, which is the scale advantage. reasoning_effort is set to high because diagnosing root cause actually requires inference. Low adoption could mean internal change at the customer, a missing feature, poor onboarding, or pricing pressure - same usage pattern, completely different intervention.

The Success Playbooks KB is the design decision I'm most proud of here. Instead of hardcoding intervention logic in the prompt, it lives in a separate text KB the agent reads at runtime. That means the playbooks can be updated without touching the deployment - essential for a CS practice that needs to iterate.

Build Process
  1. Identified root cause classification as the core challenge - same symptoms, different causes require different interventions
  2. Built account profiles KB (table, LOOKUP) with health score, seat utilization, feature adoption gaps, open tickets, NPS score, and renewal date
  3. Built product docs KB (table, SEARCH) for accurate feature and how-to responses - prevents hallucinated product guidance
  4. Designed Success Playbooks as a text KB rather than prompt logic - intervention sequences by risk tier that can be updated without redeployment
  5. Set reasoning_effort: high for accurate root cause diagnosis across six possible causes
  6. Wrote escalation rules with hard thresholds: competitor mention, pricing discussion, frustrated support, renewal within 60 days with high risk
  7. Output schema captures churn risk level, root cause, intervention taken, CSM escalation flag, and renewal at risk flag
Business Value

In B2B SaaS, churn directly erodes ARR and win-back is expensive. An agent that gets in front of at-risk accounts before the renewal conversation preserves revenue that would otherwise require a campaign to recover - or just be gone.

  • Covers every account continuously without adding headcount
  • Root cause classification means the intervention actually fits the problem
  • Escalation flags keep CSMs focused on the accounts that genuinely need them
  • Output feeds CDP segments for renewal risk dashboards and proactive outreach

Multi-Agent

Customer Success Orchestrator

Routes incoming customer requests to specialist agents using agent-to-agent tool wiring. The most advanced pattern in the portfolio.

Agent-to-agent tools reasoning: high output_mode: RETURN test.yml included
Logic and Context

This one is built differently. Instead of knowledge bases as tools, two specialist agents are wired as tools - the Subscriber Re-engagement Agent and the Churn Risk Intervention Agent. That's the agent-to-agent pattern.

The orchestrator's job is to route, not resolve. A message comes in, it reads the routing rules, decides whether this is a B2C subscriber or a B2B account, calls the right specialist, and relays the response. The customer sees one conversation.

output_mode: RETURN on both tools means responses come back to the orchestrator before the customer sees them. The alternative, SHOW, would stream the specialist's response directly to the customer. That's useful in some cases - but here the orchestrator needs to control what goes out.

Build Process
  1. Identified the use case: enterprises with multiple customer types hitting one entry point need intelligent routing, not a single monolithic agent
  2. Deployed specialist agents first (media-streaming and b2b-saas) - orchestrator requires them to exist before it can reference them via @ref
  3. Wired specialist agents as tools using type: agent rather than type: knowledge_base - the key architectural difference
  4. Set output_mode: RETURN on both tools so responses return to orchestrator for synthesis before delivery
  5. Wrote routing rules in prompt.md with keyword signals for B2C vs B2B disambiguation
  6. Added explicit guardrail: do not expose specialist agent names to the customer
  7. Wrote test cases covering routing accuracy, ambiguous input handling, and specialist name exposure

Business Value

Large accounts often have both consumers and business customers hitting the same support channel. Without routing, they get a generic response or get bounced to the wrong team. The orchestrator puts the right specialist in front of the right customer every time.

  • One entry point, multiple specialists behind it
  • Fewer contacts bounced to the wrong team
  • Adding a new specialist doesn't change anything from the customer's side
  • The routing decision feeds the CDP for customer type classification and journey assignment
