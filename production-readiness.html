Identity and Consent

B2B identity is simpler than B2C - you're working with account-level records, not individual consumer profiles. But consent still matters.

Identity Resolution
  1. Account identity is resolved via account_id, passed as a variable at conversation start. No fuzzy matching needed - the CRM is the authoritative source.
  2. Individual user identity (the CSM or account contact initiating the session) is handled at the platform level. Treasure AI authenticates the session before the agent runs. The agent never processes individual PII directly.
  3. Returning account recognition uses prior conversation history from agent_output, not personal identifiers. The agent sees account context, not who is typing.
Consent Handling
  1. The consent_b2b field in account_profiles flags whether a Data Processing Agreement is signed. If false, the agent limits itself to generic product guidance - no account-specific data is surfaced.
  2. All data written to agent_output is tagged with account_id only, not user email or name. Compliant with GDPR Article 25 data minimisation.
  3. In EMEA, employee data (usage patterns, login behavior) falls under GDPR. The DPA covers this at contract level. No additional per-user consent flow is needed for B2B account health use cases.
  4. Retention policy on agent_output: 24 months, aligned with standard B2B contract cycles. After that, records are anonymised rather than deleted so trend data is preserved.

Testing Strategy

test.yml handles unit-level behavior. Getting to production requires three more layers on top of that.

Four Testing Layers
  1. Unit tests (test.yml) - smoke, behavior, escalation, and regression cases. Covers expected inputs, guardrail enforcement, and edge cases like missing KB data or ambiguous signals. Already in place. Runs on every push via tdx agent test.
  2. Shadow mode (2 weeks pre-launch) - deploy the agent alongside human CSMs for two weeks. It processes the same accounts but output is logged only, not acted on. Compare agent churn_risk scores against CSM assessments. Target: agreement rate above 80% before going live. Disagreements get reviewed to update either the agent or the comparison baseline.
  3. Staged rollout - start with 10% of the account base, biased toward medium-risk accounts where errors are recoverable. Monitor escalation rate and CSM override rate for the first 30 days before expanding to full coverage. A sharp spike in either metric is a stop signal.
  4. Adversarial testing - run accounts with deliberately noisy data: missing fields, conflicting signals, stale records. Verify the agent degrades gracefully - it should default to escalate_to_csm = true when confidence is low, not force a classification. Confident wrong answers are worse than honest uncertainty.
  5. Regression on updates - any change to prompt.md or success_playbooks.md triggers a full test.yml run plus a comparison against the last 30 days of live output. Flag any shift in root_cause distribution greater than 15%. That kind of shift usually means the update introduced unintended behavior.

Failure Handling

Five categories of failure, each with a defined response. No silent errors, no guessing.

Failure Playbook
  1. KB returns no data - account_id not found or data pipeline delayed. The agent responds with generic product guidance, sets escalate_to_csm = true, and logs root_cause = data_unavailable. It never fabricates account context to fill the gap.
  2. Ambiguous root cause - multiple signals point in different directions and no clear pattern emerges. The agent surfaces what it found, states that confidence is low, and escalates rather than forcing a classification. A confident wrong answer is worse than an honest handoff.
  3. Out-of-scope input - billing disputes, legal requests, executive escalations. Prompt guardrails catch these and route immediately to the appropriate team. No attempt is made to handle outside the agent's remit.
  4. Platform-level outage - Treasure AI service unavailable. A static fallback response acknowledges the issue and provides CSM contact details. The output write is queued and retried on recovery rather than dropped entirely.
  5. Playbook gap - the account situation does not match any pattern in success_playbooks.md. The agent defaults to escalate_to_csm = true and logs root_cause = needs_review. This feeds the next playbook update cycle - over time, repeated needs_review cases become new playbook entries.

Proving Business Impact

The agent needs a baseline to measure against. Without one, any improvement in renewal rates could be seasonal, market-driven, or coincidental.

Control Group Setup
  1. At rollout, randomly assign 20% of eligible accounts to a holdout group. These accounts receive standard CSM coverage only - no agent intervention.
  2. Match holdout accounts to treatment accounts on health score, ARR tier, and renewal date to reduce selection bias. The groups should look similar going in.
  3. Run the split for a full renewal cycle - minimum 90 days - before drawing conclusions. Shorter windows pick up noise, not signal.
  4. Primary metric: renewal rate. Secondary metrics: time-to-escalation for high-risk accounts, CSM hours per account, NPS score at renewal.
  5. Do not adjust the control group mid-experiment. Once you start, the holdout stays until the window closes.
