Identity and Consent

B2B is simpler than B2C here - you're dealing with account-level records, not individual consumer profiles. But consent still matters, especially in EMEA.

Identity Resolution
  1. The account gets identified by its account_id, passed in as a variable before the conversation starts. The CRM is the source of truth - no fuzzy matching needed.
  2. Who is actually typing - the CSM or account contact - gets handled at the platform level. Treasure AI authenticates the session before the agent runs. The agent itself never touches individual PII.
  3. When the agent looks up prior history, it pulls from agent_output using account_id, not personal identifiers. It sees account context, not who's on the other end.
Consent Handling
  1. There's a consent_b2b field in account_profiles that flags whether a Data Processing Agreement is signed. If it's false, the agent sticks to generic product guidance - no account-specific data gets surfaced.
  2. Everything written to agent_output is tagged with account_id only. No email addresses, no names. That keeps it compliant with GDPR Article 25 on data minimisation.
  3. In EMEA, employee usage data falls under GDPR. The DPA at contract level covers this - no separate per-user consent flow is needed for account health use cases.
  4. agent_output records are kept for 24 months, which lines up with standard B2B contract cycles. After that they're anonymised rather than deleted, so the trend data stays intact.

Testing Strategy

test.yml covers the unit-level stuff. Actually getting to production takes a few more steps on top of that.

Four Testing Layers
  1. Unit tests (test.yml) - smoke, behavior, escalation, and regression cases. Covers expected inputs, guardrail enforcement, and edge cases like missing KB data or conflicting signals. Already built. Runs on every push via tdx agent test.
  2. Shadow mode (2 weeks pre-launch) - run the agent alongside CSMs for two weeks. It looks at the same accounts but nothing it decides gets acted on yet - just logged. Compare the agent's churn_risk scores against what the CSMs actually think. You want agreement above 80% before going live. Where they disagree, figure out why - sometimes the agent is wrong, sometimes the CSM baseline needs updating.
  3. Staged rollout - start with 10% of accounts, biased toward medium-risk ones where a mistake is recoverable. Watch the escalation rate and how often CSMs override the agent in the first 30 days. Either of those spiking is a reason to pause before expanding.
  4. Adversarial testing - feed it accounts with bad data on purpose. Missing fields, conflicting signals, stale records. The agent should admit uncertainty and escalate, not force a classification. A wrong confident answer causes more damage than an honest handoff to a CSM.
  5. Regression on updates - any change to prompt.md or success_playbooks.md triggers a full test.yml run and a comparison against the last 30 days of live output. If the root_cause distribution shifts by more than 15%, something unintended changed and you need to find it before it ships.

Failure Handling

Five things that can go wrong, and what happens in each case.

Failure Playbook
  1. KB returns no data - account_id not found or the data pipeline is delayed. The agent falls back to generic product guidance, flags escalate_to_csm = true, and logs root_cause = data_unavailable. It doesn't try to fill the gap by guessing.
  2. Ambiguous root cause - signals are pointing in multiple directions with no clear answer. The agent tells the CSM what it found, flags low confidence, and hands off. Forcing a classification when the data is unclear causes more problems than admitting it doesn't know.
  3. Out-of-scope input - billing disputes, legal requests, executive escalations. These get caught by prompt guardrails and routed to the right team immediately. The agent doesn't try to handle things it's not built for.
  4. Platform outage - Treasure AI is unavailable. A static response goes out acknowledging the issue with CSM contact details. The output write gets queued and retried when the service comes back, not dropped.
  5. Playbook gap - the account doesn't match any pattern in success_playbooks.md. The agent escalates and logs root_cause = needs_review. Over time those cases get reviewed and turned into new playbook entries. The gaps are actually useful - they show you where the playbook needs to grow.

Proving Business Impact

You need a baseline to compare against. Without one, better renewal rates could just be a good quarter - not the agent working.

Control Group Setup
  1. At rollout, randomly assign 20% of eligible accounts to a holdout group. They get normal CSM coverage, no agent. That's your control.
  2. Match the holdout accounts to the treatment group on health score, ARR tier, and renewal date. You want both groups to look similar going in, otherwise you're not comparing like for like.
  3. Run the split for at least 90 days - a full renewal cycle. Shorter windows are noise, not signal.
  4. Primary metric is renewal rate. Secondary: how fast high-risk accounts get escalated to a CSM, CSM time per account, and NPS at renewal.
  5. Don't touch the control group once you start. The holdout stays as-is until the window closes.
